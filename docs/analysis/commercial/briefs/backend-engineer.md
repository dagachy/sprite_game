# 실무 전달 브리핑: 백엔드 엔지니어용 (탕탕특공대 / 탕탕에이스 분석)

- 대상: `backend-engineer`
- 근거 문서: `docs/analysis/commercial/tangtang_analysis.md` (§1.6, §1.7, §1.8, §2.6, §4 #7~#10, §5)
- 원칙: 원작 서버 구조, API, 결제 흐름을 추정하거나 역분석하지 않는다. 공개 정보에서 확인되지 않은 경제 수치는 설계 입력으로 쓰지 않는다.

## 1. 한 줄 요약
백엔드의 핵심은 **방치 수익의 시간 계산과 상한, 일일 변형 규칙의 원격 설정, 재화 장부의 정합성**이다. 과금 구조는 아직 우리가 정하지 않았으므로 결제 연동은 뒤로 미룬다.

## 2. 구현해야 할 것 (우선순위순)

### [상] 방치 수익(순찰) 계산 모듈
- 적립 상한과 수령 최소 간격을 원격 설정 값으로 둔다. 값은 코드에 박지 않는다.
- 서버 시각 기준으로 계산한다. 클라이언트 시각을 신뢰하지 않는다(치트 방지).
- 수령 시 적립분을 0으로 돌리고, 같은 적립분이 두 번 지급되지 않도록 멱등 처리한다.
- 분석의 관찰: 적립 상한을 두면 "더 쌓이지 않음"이 생긴다. 상한 도달 시각을 응답에 포함해 UI가 표시할 수 있게 한다.

### [상] 재화 장부(원장)
- 재화 종류(예: 판 내 재화, 판 밖 재화, 에너지, 부활 재화)를 명확히 나눈다. 재화 수량은 직접 덮어쓰지 않고 **증감 이벤트 로그**에서 합산하는 방식을 권장한다.
- 판 종료 결과 적용은 한 번만 실행되도록 트랜잭션 키를 둔다. 네트워크 재시도로 중복 지급되지 않게 한다.
- 분석의 교훈: 재료 요구량이 기하급수로 늘면 디버깅과 밸런스 검토가 어려워진다. 장부에 "무엇을 얼마나 썼는지" 기록을 남겨 economy-balance-analyst가 검토할 수 있게 한다.

### [상] 원격 설정 (밸런스 값)
- 일일 변형 규칙(강화 1 + 부작용 1 짝), 방치 상한, 감속 계수 같은 값을 원격 설정으로 내려보낸다.
- 설정 버전을 붙이고, 클라이언트가 설정 버전을 기록해 문제 발생 시 추적할 수 있게 한다.

### [중] 세이브 동기화
- 판 밖 성장 데이터(장비, 파일럿, 기체 등)를 서버와 동기화한다. 충돌은 "서버 장부 우선 + 클라이언트 로그 재생" 방식을 기본으로 한다.
- 익명 계정으로 시작하고, 소셜 로그인은 나중에 붙인다. 원작에 친구 기능이 없었던 점을 참고해 소셜 기능은 우선순위를 낮춘다(분석 §1.7).

### [중] 분석 이벤트 수집
- 최소 이벤트: 판 시작, 판 종료(결과, 시간, 선택한 빌드), 방치 수령, 일일 도전 참여, 출석, 재화 증감 요약.
- 명세는 live-ops-analytics와 맞춘다. 이벤트 이름과 파라미터를 먼저 확정한다.

### [하, 보류] 결제 영수증 검증
- 과금 구조(판매 상품, 가격, 확률 공개 여부)가 정해지기 전까지 구현하지 않는다. bm-expert와 store-compliance-specialist의 결정 후 진행한다.
- 결제 설계 시 참고: 원작의 상품 구조(보석, 월정액, 챕터별 패키지)는 참고만 한다. 우리 가격 값은 확정하지 않는다.

## 3. 하지 말 것
- 원작의 보석, 에너지, 훈장 등 재화 이름과 수치를 그대로 쓰지 않는다.
- 확률 값(분석의 뽑기 확률은 나무위키 기재로 미확인)을 구현에 쓰지 않는다. 확률 공개를 한다면 우리 기준으로 새로 정한다.
- 달성 불가능한 보상을 설계하지 않는다(분석 §1.10 반면교사). 모든 보상 경로는 도달 가능성을 검증한다.

## 4. 열린 질문
- 무과금 플레이어가 한 달 안에 도달할 수 있는 성장 상한. 기준을 economy-balance-analyst와 정한다.
- 에너지 제도를 쓸지 여부. 쓴다면 회복 값을 원격 설정으로 둔다. 원작 자료에서 회복 수치가 엇갈려 확정하지 않았다.

## 5. 완료 기준
- 방치 수령을 두 번 호출해도 지급이 한 번만 된다(멱등성 테스트).
- 재화 잔액이 증감 로그 합계와 항상 일치한다(정합성 테스트).
- 원격 설정 값을 바꾸면 앱 재실행 없이 다음 판부터 반영된다.
